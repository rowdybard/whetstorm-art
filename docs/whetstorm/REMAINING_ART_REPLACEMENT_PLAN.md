# Remaining Whetstorm art replacement plan

Snapshot: 2026-10-28. This is an execution plan, not a release clearance. The art branch is a partial source checkout; `D:/whetstorm-deploy` is the complete game checkout inspected at `587f70cca1ae201fc9341e81c5f065110f71d15c`. Reconcile against the actual release revision and its build output before acting. `CREDITS.md` is the operative media register; code's MIT license does not cover media. Its records, mapping files and source evidence control over names inserted by the rebrand. Never relabel inherited work as Whetstorm-owned.

## Scope, priorities and decisions

Deliver a commercial game with the existing gameplay and readable UI intact. Required means records say no redistribution or noncommercial-only audio in a commercial build; unknown provenance also blocks inclusion until resolved. `With the project only` is permitted in a fork by the register, subject to its restriction on standalone redistribution; retain it by default and put stylistic replacement in a later optional lane. Keep verified CC0 and permissive third-party assets with their notices. Do not infer ownership from a folder, a generated image, or an unused URL. Treat brand marks individually: remove unneeded upstream branding and disabled-commerce marks; retain third-party marks only where their actual use and trademark conditions are verified.

Execute in independent batches without routine owner checkpoints. No paid generation, Tripo spend, or 3D model generation is authorized by this plan. Use original hand-authored or deterministic art, compatible existing Whetstorm assets, or appropriately licensed reusable assets with recorded provenance. Do not claim that procedural item stand-ins are completed individual paintings. If an individually painted asset cannot be authored with available tools without paid generation, leave it queued and report the blocker; proceed with other families. No copying, converting, tracing or imitating protected game assets. Reuse is allowed when the item identity truly permits it, explicitly recorded per ID. Do not invent future class or item IDs.

Work order follows `ART.md` and the owner brief: preserve existing title and launch-class work; finish launch-kit and essential HUD needs; address Old Peatfire and launch weapons/arena where replacement is actually needed; then current items in encounter order and Book of Deeds. Physical removal of prohibited media and a usable fallback precede any public build even for later visual polish. Retired nine-class skills, generated target portraits, terrain maps and licensed free-pack scenery are not new illustration priorities. Store/Claudium is removal, not a new art commission. If those retired assets remain present in `public`, they still require disposition.

## Inventory ledger and gates

1. Freeze the candidate revision and record checkout status, build command and output paths. Inventory every physical asset under `public`, native shells (`android`, `ios`, `electron`, `build`), website and guide, generated or packed media, and any other files copied into the release. Record relative path, byte size, SHA-256, source/master, owner, grant, attribution, current consumers, disposition, replacement and evidence. Treat duplicate hashes as separate physical copies for removal, and as one artwork only for unique-art counts. Search both paths and hashes, plus model-embedded textures and data URIs.
2. Join each physical file to `CREDITS.md`, per-family `mapping.json`, `docs/achievements` lineage, generation records and build manifests. Mark `required removal/replacement`, `unknown`, `fork-permitted`, `CC0/permissive`, or `original Whetstorm`; retain evidence and separate attribution requirements. Unmapped and contradictory claims remain unknown. Check actual license notices and preserve them. A history-only restricted source can still be a distribution concern for a repository release.
3. Cross-check runtime references, manifests, CSS, hardcoded paths, editor/wiki/native consumers, service-worker caches and generated bundles. Switch consumers, remove every restricted or unknown distributed copy, regenerate owning manifests and verify paths and hashes in a clean built package. Do not remove files solely because a static search found no references. Disabled features do not exempt public files from distribution.
4. Maintain a per-batch ledger: IDs, physical paths, hashes, source and lineage, references, export command/settings, deliberate reuse, acceptance, failures, open review, and tests. Keep old records truthful and preserve provenance evidence in a nonshipping location only where distribution rights allow it. Never edit generated manifests by hand.

## Validation and completion

For each batch verify actual file decoding, dimensions, alpha, hashes, provenance, no unintended duplicate art, full catalog mapping and all relevant fallback paths. Run focused asset and routing tests; validate models, rigs and collision where touched, SFX conformance where audio changes, and accessibility, responsive and screenshot checks for UI. Capture before/after desktop and mobile browser evidence and inspect real gameplay; report if unavailable. Respect sim, parity and performance invariants, and use the relevant local `CLAUDE.md` and specialist review for changed surfaces. Run `node scripts/gate_select.mjs` in the complete checkout as the pre-merge gate, or the deeper `npm run gate` where required, and record exact outcomes and blocked checks. Never call focused tests a full gate.

Release readiness additionally requires a fresh candidate build, full physical file and hash comparison against the ledger, zero prohibited or unclassified media in each distribution artifact, correct attribution notices, no broken runtime references and no stale cached copies. Independently inspect the actual deployment and native artifacts when they exist; this plan does not authorize deployment, remote mutation, or release. Any permissions received later must be written, asset-specific, cover commercial distribution and be recorded before treating a blocked file as usable.

Only ask the owner when a choice cannot be made safely from existing authority: a requested paid service or 3D generation, a disputed license that cannot be resolved or replaced, a change to gameplay/feature removal beyond a safe visual substitution, access to an unavailable delivery target, or a release/deployment decision. Ordinary batch order, compatible reuse, art decisions and routine verification proceed autonomously. If the environment lacks image production or full-game testing, document the exact capability gap, leave the affected work open, and keep executing independent packages.
